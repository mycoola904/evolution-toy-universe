# PostgreSQL Persistence Implementation Plan

## Purpose

Move completed-experiment persistence from SQLite to PostgreSQL on the
`feature/postgresql-persistence` branch while preserving the current simulation
and recording behavior.

The local PostgreSQL databases already created for this work are:

- `evolution_toy_universe` for normal experiments;
- `evolution_toy_universe_test` for automated tests.

This plan has been reviewed and accepted with the decisions recorded below. It
does not authorize importing or deleting existing SQLite data.

## Current State

The persistence boundary is already small and well separated from the domain:

- `src/persistence/database.py` owns SQLite connections, schema creation, and
  the current schema-version/backfill logic;
- `src/persistence/experiment_recorder.py` saves a run and all organism results
  in one transaction;
- `src/main.py` selects a SQLite path with `--database`, initializes the schema,
  and treats persistence failures as fatal;
- `tests/test_database.py`, `tests/test_experiment_recorder.py`, and parts of
  `tests/test_main.py` depend directly on SQLite behavior;
- `README.md`, `docs/10-technical-design.md`, and
  `src/persistence/__init__.py` describe SQLite as the active store.

The existing suite has 75 passing tests when pytest is given a writable local
temporary directory. That is the behavioral baseline for this change.

`requirements.txt` already contains Psycopg 3 packages as an uncommitted branch
change. Preserve that work while normalizing the dependency declaration and
file encoding during implementation.

## Review Decisions

1. **PostgreSQL is the only supported runtime backend.** Do not add a generic
   database abstraction or maintain dual SQLite/PostgreSQL SQL paths.
2. **Use Psycopg 3 directly.** The project has two tables and does not need an
   ORM, Alembic, or connection pool for its current one-write-per-experiment
   workload.
3. **Use environment-provided connection strings only.** Read normal runs from
   `DATABASE_URL` and database tests from `TEST_DATABASE_URL`. Remove the
   path-based `--database` option and do not replace it with `--database-url`;
   command-line connection strings can expose credentials through shell history
   and process inspection. Load the ignored repository-root `.env` file without
   overriding existing process variables. Do not commit credentials or silently
   fall back from the test database to the normal database.
4. **Use native PostgreSQL types.** In particular, use `TIMESTAMPTZ`, `BOOLEAN`,
   and `JSONB` instead of storing those values as SQLite-compatible text or
   integers.
5. **Use versioned, transactional SQL migrations.** Replace `PRAGMA
   user_version` and schema inspection/backfill methods with an explicit
   `schema_migrations` table and ordered SQL files.
6. **Do not import historical SQLite data.** The two PostgreSQL databases are
   new targets. Existing SQLite records are intentionally outside the scope of
   this branch.
7. **Use one local PostgreSQL role for both databases.** The normal and test
   DSNs will use the same role, while database-name validation prevents test
   cleanup from targeting the normal database.
8. **Require the exact test database name.** Destructive test setup is allowed
   only when `TEST_DATABASE_URL` resolves to
   `evolution_toy_universe_test`. Broader `_test` naming can be considered later
   if CI requires dynamically named databases.

## Scope

### Included

- PostgreSQL connection configuration and validation;
- PostgreSQL schema and migration runner;
- Psycopg-based experiment recording;
- PostgreSQL integration tests using `evolution_toy_universe_test`;
- CLI, dependency, and documentation updates;
- end-to-end verification against both created databases.

### Excluded

- changing simulation behavior or result contents;
- persisting live/per-tick simulation state;
- connection pooling;
- asynchronous database access;
- automatic database or PostgreSQL-role creation;
- deployment/hosted PostgreSQL setup;
- deleting SQLite files;
- historical SQLite data import.

## Target Design

```text
Simulation
    -> immutable ExperimentResult snapshot
    -> ExperimentRecorder
    -> ExperimentDatabase / Psycopg transaction
    -> PostgreSQL
         schema_migrations
         simulation_runs
         organism_results
```

The simulation remains entirely in memory. PostgreSQL records only a completed
experiment. Building or saving the result must not consume random numbers or
otherwise alter deterministic simulation behavior.

### PostgreSQL Type Mapping

| Current value | PostgreSQL type | Notes |
|---|---|---|
| generated row IDs | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Retrieve with `RETURNING id`. |
| run/organism/tick/count integers | `BIGINT` or `INTEGER` according to expected range | Run-local organism IDs and foreign keys must use matching types. |
| `started_at` | `TIMESTAMPTZ` | Keep the application value timezone-aware and normalized to UTC. |
| `git_dirty` | `BOOLEAN` | Preserve `NULL` as unknown. |
| run configuration | `JSONB` | Pass dictionaries through Psycopg's JSON adapter. |
| genome | `JSONB` | Compare decoded values in tests; do not depend on JSON key order. |
| energy values | `DOUBLE PRECISION` | Preserve current Python float behavior. |
| reason, commit hash | `TEXT` | Preserve current nullable/non-nullable rules. |

Retain the current constraints and index unless a separate schema change is
approved:

- foreign key from `organism_results.simulation_run_id` to
  `simulation_runs.id`;
- uniqueness of `(simulation_run_id, organism_id)`;
- non-negative `mutated_weight_count` when it is present;
- `idx_organism_results_parent` on
  `(simulation_run_id, parent_organism_id)`.

## Implementation Phases

### Phase 1: Finalize Dependencies and Connection Configuration

Files:

- `requirements.txt`
- `src/persistence/database.py`
- `src/main.py`
- `tests/test_main.py`

Work:

1. Normalize `requirements.txt` to UTF-8 and declare the selected Psycopg 3
   binary installation once (for example, a pinned `psycopg[binary]` entry)
   rather than treating `psycopg` and `psycopg-binary` as two application
   dependencies.
2. Replace `DEFAULT_DATABASE_PATH` and `Path`-based database state with a
   PostgreSQL connection string.
3. Resolve `DATABASE_URL` only when persistence is enabled. `--no-persist` must
   continue to skip database configuration, Git inspection, initialization,
   and writes.
4. Remove `--database PATH` without adding a DSN command-line replacement.
   Environment variables are the sole connection-configuration path; this
   keeps passwords out of command history and process arguments.
5. Fail early with a concise configuration error when persistence is enabled
   and no usable normal-run DSN is supplied.
6. Rename path-oriented parameters, output, and tests (`database_path`) to
   connection-oriented names (`database_url` or `connection_info`). Do not call
   `.resolve()` on a DSN or print credentials in the success message.

Acceptance criteria:

- normal persistence cannot accidentally target a local SQLite file;
- `--no-persist` works with neither database environment variable set;
- logs identify the target database safely, without echoing a password;
- existing fatal-on-persistence-error behavior is retained.

### Phase 2: Add PostgreSQL Schema Migrations

Files:

- `src/persistence/database.py`
- `src/persistence/migrations/001_initial_schema.sql` (new)
- `src/persistence/migrations/__init__.py` if package-resource loading is used
- `tests/test_database.py`

Work:

1. Replace `sqlite3.connect()` with `psycopg.connect()` and keep connection
   lifetime scoped through context managers.
2. Add `schema_migrations` with at least `version`, `name`, `checksum`, and
   `applied_at`. PostgreSQL migration numbering starts at `001`; it does not
   need to mirror SQLite's `PRAGMA user_version = 2`.
3. Put the current complete two-table schema into the first PostgreSQL migration
   using the native types above.
4. Make `ExperimentDatabase.initialize()`:

   - acquire a transaction-scoped PostgreSQL advisory lock dedicated to schema
     migration;
   - create/read `schema_migrations`;
   - reject migration versions unknown to the application;
   - reject a checksum mismatch for an already-applied migration;
   - apply pending migrations in order;
   - record each applied migration in the same transaction as its SQL;
   - roll back the initialization transaction on any failure.

5. Remove SQLite-only code: directory creation, foreign-key PRAGMA, script
   execution assumptions, schema PRAGMAs, and the runtime legacy mutation-count
   backfill.
6. Preserve a persistence-specific migration exception with messages that name
   the failed migration without exposing credentials.

The advisory lock matters because PostgreSQL is shared: two experiments may
start at the same time and both call `initialize()`.

Acceptance criteria:

- initialization creates all three tables and the parent index in an empty
  PostgreSQL schema;
- a second initialization is a no-op;
- constraints are enforced by PostgreSQL;
- failed migrations leave neither partial schema changes nor migration rows;
- an unexpected newer or modified migration is rejected clearly.

### Phase 3: Port the Recorder to Psycopg

Files:

- `src/persistence/experiment_recorder.py`
- `src/experiments/results.py`
- `tests/test_experiment_recorder.py`

Work:

1. Change DB-API placeholders from `?` to Psycopg's `%s` placeholders.
2. Insert the run with `INSERT ... RETURNING id` and fetch that value instead
   of using SQLite's `lastrowid`.
3. Pass configuration and genome dictionaries with Psycopg's `Jsonb` adapter;
   remove `json.dumps()` from write code.
4. Store `git_dirty` as `bool | None` without integer conversion.
5. Change `SimulationRunResult.started_at` to a timezone-aware `datetime`, or
   convert it at the persistence boundary, so `TIMESTAMPTZ` never receives a
   naive timestamp. Prefer the typed result value because it prevents invalid
   snapshots before persistence.
6. Keep the run insert and all organism inserts inside one transaction. A
   duplicate organism or any other write failure must roll back the run too.
7. Continue using batch insertion for organism rows. Do not introduce a pool or
   copy protocol until experiment sizes show a measured need.

Acceptance criteria:

- the returned run ID is the PostgreSQL-generated identity;
- nullable provenance and lineage fields retain their meaning;
- JSONB round-trips to values equal to the source dictionaries;
- zero and `NULL` mutation counts remain distinct;
- a failed organism insert leaves zero rows for that experiment.

### Phase 4: Rebuild Persistence Tests Around the Test Database

Files:

- `tests/conftest.py`
- `tests/test_database.py`
- `tests/test_experiment_recorder.py`
- `tests/test_main.py`
- `pytest.ini` if a PostgreSQL marker is introduced

Work:

1. Add a session-scoped fixture that requires `TEST_DATABASE_URL` for tests
   that access PostgreSQL.
2. Parse the DSN and fail closed unless its database name is exactly
   `evolution_toy_universe_test`. Also reject a test DSN equal to
   `DATABASE_URL`.
3. Initialize the test schema and isolate each persistence test by truncating
   only the known application tables with `RESTART IDENTITY CASCADE` before or
   after the test. Never drop the database and never clean a database that
   failed the name guard.
4. Replace SQLite catalog/PRAGMA assertions with `information_schema` or
   `pg_catalog` queries for tables, columns, constraints, indexes, and applied
   migrations.
5. Replace `sqlite3.IntegrityError` assertions with Psycopg exceptions.
6. Use Psycopg row factories when mapping rows by column name.
7. Retain tests for:

   - idempotent initialization;
   - foreign-key enforcement;
   - negative mutation-count rejection;
   - complete run/organism round-trip;
   - transaction rollback on duplicate organisms;
   - inclusion of dead organisms and reproduction lineage;
   - no-persist short-circuiting;
   - fatal connection/initialization/write errors.

8. Replace the SQLite legacy-backfill tests with migration-runner tests. Remove
   the legacy SQLite backfill algorithm because historical import is explicitly
   out of scope.

Acceptance criteria:

- the test suite never opens or modifies `evolution_toy_universe`;
- repeated local test runs start from a known state;
- failed tests do not leave committed experiment rows;
- non-persistence tests remain independent of PostgreSQL where practical;
- the complete suite passes against `evolution_toy_universe_test`.

### Phase 5: Update Application and Documentation Language

Files:

- `README.md`
- `docs/10-technical-design.md`
- `src/persistence/__init__.py`
- `.gitignore` only if obsolete SQLite artifacts are intentionally retired

Work:

1. Replace SQLite setup, path, failure, and query examples with PostgreSQL
   terminology and PowerShell examples for setting `DATABASE_URL` and
   `TEST_DATABASE_URL`.
2. Document prerequisites: running PostgreSQL, existing databases, a role with
   connect plus schema/table/migration privileges, and no committed password.
3. Document schema initialization as automatic application migration, while
   making clear that database/role creation is an operator task.
4. Update JSON wording to describe semantic JSONB values rather than relying on
   serialized key order.
5. Update the package docstring and CLI help/output.
6. Leave SQLite ignore patterns in place while any legacy `.db` files are
   retained; ignoring them is harmless and prevents an accidental legacy-data
   commit.

Acceptance criteria:

- no active instructions claim SQLite is the runtime store;
- a new developer can configure normal and test connections without editing
  source code;
- examples do not expose real credentials.

### Phase 6: End-to-End Verification

1. Run all unit and PostgreSQL integration tests against
   `evolution_toy_universe_test`.
2. Start with an empty normal schema, run a short seeded experiment against
   `evolution_toy_universe`, and record the returned run ID.
3. Re-run initialization to verify migration idempotence.
4. Query the stored run and its organism count, configuration, provenance,
   lineage, and mutation counts.
5. Force a constraint violation in the test database and verify whole-run
   rollback.
6. Run the same seed with `--no-persist` and confirm that no connection is
   attempted and simulation behavior is unchanged.
7. Run the full suite a second time to prove cleanup and repeatability.
8. Inspect `git diff` to ensure no DSNs, passwords, generated database files,
   or test data are present.

## Suggested Commit Sequence

1. `Configure PostgreSQL persistence dependency and connection settings`
2. `Add transactional PostgreSQL schema migrations`
3. `Port experiment recording to Psycopg`
4. `Run persistence tests against the PostgreSQL test database`
5. `Document PostgreSQL experiment persistence`

Keep schema/recorder changes and their tests in the same commit when practical;
the exact split may be adjusted to keep every commit runnable.

## Risks and Mitigations

- **A test erases normal experiment data.** Require a dedicated test DSN,
  validate its database name, reject equality with the normal DSN, and truncate
  only after those checks pass.
- **Credentials leak through source, logs, or process arguments.** Use ignored
  environment files or session environment variables, sanitize connection
  errors/output, and never print the full DSN.
- **Concurrent startup races during schema creation.** Serialize migrations
  with a PostgreSQL advisory transaction lock.
- **PostgreSQL transaction-aborted behavior surprises tests.** Put expected
  constraint failures in their own connection/transaction; after an integrity
  error, roll back before issuing more statements.
- **JSON behavior changes.** Assert decoded value equality and use JSONB
  adapters; do not assert serialized whitespace or key order.
- **Timestamp behavior changes.** Accept only timezone-aware values and verify
  UTC round-trips.
- **Historical SQLite results are not migrated.** This is an accepted review
  decision. Leave any source SQLite file untouched; it is not used by the new
  runtime.
- **A shared server is unavailable.** Surface connection failures immediately
  for persistence tests and normal writes; retain `--no-persist` for simulation
  work that intentionally does not require a database.

## Before Implementation: Local Prerequisites

The user does not need to create tables, indexes, migration records, or a new
PostgreSQL role. The implementation will create application schema objects, and
the already-created databases will be used.

Before integration tests and end-to-end verification, confirm that the one
local role:

- can connect to both `evolution_toy_universe` and
  `evolution_toy_universe_test`;
- can use and create objects in the target schema (normally `public`);
- can create tables, indexes, constraints, and migration records;
- owns the application objects it creates, so tests can truncate the two
  application tables in the test database.

Set both connection strings in the environment seen by the application and
test process. A PowerShell session example is:

```powershell
$env:DATABASE_URL = "postgresql://ROLE:PASSWORD@localhost:5432/evolution_toy_universe"
$env:TEST_DATABASE_URL = "postgresql://ROLE:PASSWORD@localhost:5432/evolution_toy_universe_test"
```

Replace the placeholders locally. Do not paste the real password into chat,
source files, documentation, or a committed shell script. If the password
contains URI-reserved characters such as `@`, `:`, `/`, `?`, or `#`, percent-
encode those characters in the URI. If local PostgreSQL authentication does not
require a password, omit the password component rather than inventing one.

These variables should ideally be configured before implementation begins so
connection and migration tests can be run as the code is developed. Most code
can be written without them, but the branch cannot meet its definition of done
until both database connections are available to the test process. Environment
variables set in one PowerShell window apply only to that process and its child
processes; restart the IDE/agent after setting persistent user-level variables,
or launch it from the configured shell.

## Definition of Done

The branch is complete when a deterministic experiment can be saved atomically
to `evolution_toy_universe`, all persistence integration tests run repeatably
and exclusively against `evolution_toy_universe_test`, schema migrations are
safe and idempotent, `--no-persist` remains database-independent, documentation
contains no active SQLite workflow, and the repository contains no credentials
or generated experiment data.
